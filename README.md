# Time Deposit Kata: Solution

The solution is a Java 21 / Spring Boot 3.5 service in [`java/`](java/). The legacy `TimeDepositCalculator.updateBalance` keeps its signature and its behaviour for every valid input but is now a facade over one interest policy per plan. Two REST endpoints, one to read all time deposits and one to update all balances, sit on top of it, backed by PostgreSQL with a Liquibase schema. The assignment text is kept unchanged at the bottom of this file.

## Run it

Prerequisites: JDK 21 and a running Docker.

```bash
cd java
./mvnw spring-boot:run
```

Spring Boot starts PostgreSQL from [`compose.yaml`](java/compose.yaml), Liquibase creates the two tables and loads thirteen sample deposits with their withdrawals, and the app listens on `http://localhost:8080`. Stop the app with Ctrl+C; the database container is removed, so the data is reset on every start.

The console log shows every API call with its status and duration, the SQL statements, how many deposits were read and saved, and a warning for each deposit with an unknown plan.

   | 3 | student | 100 | 2000.0 | 2 |
   | 4 | student | 400 | 3000.0 | none |

   | 7 | basic | 31 | 1234.56 | 1 |

3. Expand `POST /time-deposits/balance-updates`, click **Try it out**, then **Execute**. The response is `204 No Content` with no body.
4. Run `GET /time-deposits` again. Seven balances changed:

   | id | new balance | why |
   |----|-------------|-----|
   | 2 | 5004.17 | basic, 45 days: 5000 x 1% / 12 = 4.1667, rounded to 4.17 |
   | 3 | 2005.0 | student, 100 days (under 366): 2000 x 3% / 12 = 5.00 |
   | 6 | 20083.33 | premium, 90 days (over 45): 20000 x 5% / 12 = 83.3333, rounded to 83.33 |
   | 7 | 1235.59 | basic, 31 days (first day with interest): 1234.56 x 1% / 12 = 1.0288, rounded to 1.03 |
   | 8 | 100083.32 | basic, 730 days (no upper limit): 99999.99 x 1% / 12 = 83.3333, rounded to 83.33 |
   | 9 | 990.12 | student, 365 days (last day with interest): 987.65 x 3% / 12 = 2.4691, rounded to 2.47 |
   | 12 | 15816.38 | premium, 46 days (first day with interest): 15750.75 x 5% / 12 = 65.6281, rounded to 65.63 |

   The other six did not change: deposit 1 (basic, 20 days) is inside the first 30 days; deposits 4 and 10 (student, 400 and 366 days) are past the first year; deposits 5 and 11 (premium, 40 and 45 days) have not passed day 45; deposit 13 has the unknown plan `gold`, which earns nothing. Every `POST` accrues one more month of interest on the new balance (the update is not idempotent, [A3](docs/01-assumptions.md)); `days` is not incremented. Restart the app to get the sample data back.

The same calls with `curl`:

```bash
curl http://localhost:8080/time-deposits
curl -i -X POST http://localhost:8080/time-deposits/balance-updates
```

The API contract is generated by springdoc at <http://localhost:8080/v3/api-docs> and pinned by a test against the committed file [`api-docs.json`](java/src/test/resources/e2e/openapi/response/api-docs.json).

## Run the tests

```bash
cd java
./mvnw test
```

Docker must be running; the tests start their own PostgreSQL with Testcontainers and do not need Docker Compose. The suite has characterization tests of `updateBalance` (day boundaries, rounding, unknown plans), API tests for both endpoints and the OpenAPI contract against a real PostgreSQL, and ArchUnit rules for the dependency direction.

## Design in brief

```
org.ikigaidigital
├── TimeDeposit                  legacy shared class, unchanged
├── TimeDepositCalculator        legacy API, signature frozen; facade over the policies
├── TimeDepositApplication       Spring Boot main + the calculator bean
├── domain
│   ├── model                    PlanType, Withdrawal, TimeDepositDetails
│   └── policy                   InterestPolicy, Basic/Student/PremiumInterestPolicy
├── application                  TimeDepositService
│   └── port                     TimeDepositRepository (outbound port)
└── adapter
    ├── controller               TimeDepositController, TimeDepositApiMapper
    │   ├── config               OpenApiConfig, RequestLoggingFilter
    │   └── dto                  TimeDepositResponse, WithdrawalResponse
    └── persistence              JdbcTimeDepositRepository
```

- **Strategy per plan.** `updateBalance` looks up the `InterestPolicy` of each deposit's plan and applies the legacy rounding in one place. Each policy owns its rate and its eligibility window.
- **Hexagonal layout.** The domain has no Spring types; the controller and the JDBC adapter depend inward and not on each other. An ArchUnit test enforces this.
- **Adding a plan.** One `PlanType` constant, one `InterestPolicy` class, one entry in the calculator's constructor, and its boundary tests. An ArchUnit rule fails if the policy is written but not listed.
- **Backward compatibility over style.** `TimeDeposit` and `TimeDepositCalculator` stay in the root package, and the policies are listed in the calculator's no-arg constructor instead of being injected by Spring, so existing callers of `new TimeDepositCalculator().updateBalance(...)` keep working ([D5, D19](docs/03-architecture.md)).
- **Refactoring safety.** Characterization tests were written first, against the untouched legacy code, and the refactoring passed them unchanged. They were later regrouped into scenario tables in `TimeDepositCalculatorLegacyBehaviourTest`, with the same inputs and expected values.

# Time Deposit Refactoring Kata - Take-Home Assignment

## XA Bank Time Deposit

### Context
A junior developer implemented domain logic for a time deposit system but did not complete the API functionality. Your task is to refactor the existing codebase to implement all required functionalities based on the provided business requirements, ensuring no breaking changes occur.

### Requirements

1. **API Endpoints**:
    - Create a RESTful API endpoint to update the balances of all time deposits in the database.
    - Create a RESTful API endpoint to retrieve all time deposits.
        - The GET endpoint should return a list of all time deposits with the following schema:
            - `id`
            - `planType`
            - `balance`
            - `days`
            - `withdrawals`

2. **Database Setup**:
    - Store all time deposit plans in a database.
    - Define the following tables:
        - `timeDeposits`:
            - `id`: Integer (primary key)
            - `planType`: String (required)
            - `days`: Integer (required)
            - `balance`: Decimal (required)
        - `withdrawals`:
            - `id`: Integer (primary key)
            - `timeDepositId`: Integer (foreign key, required)
            - `amount`: Decimal (required)
            - `date`: Date (required)

3. **Interest Calculation**:
    - Implement logic to calculate monthly interest based on the plan type:
        - **Basic Plan**: 1% interest
        - **Student Plan**: 3% interest (no interest after 1 year)
        - **Premium Plan**: 5% interest (interest starts after 45 days)
    - No interest is applied for the first 30 days for any existing plans.

4. **Refactoring Constraints**:
    - Do not introduce breaking changes to the shared `TimeDeposit` class or modify the `updateBalance` method signature.
    - Ensure the design is extensible to accommodate future complexities in interest calculations.

5. **Code Quality**:
    - Adhere to SOLID principles, design patterns, and clean code practices where applicable.

6. **AI-Assisted Development**:
    - Set up an AI harness or agent workflow and use it throughout the development for this take-home exercise.
    - Briefly document the tools and setup used (e.g., LLMs, coding assistants, agentic frameworks, configuration).
    - Ensure your AI setup is practical and reproducible.
    - Include any custom rules, system prompts, or agent configurations used.
    - Include a brief summary of which parts of the solution were AI-assisted and why.

### Important Guidelines
- The existing `TimeDepositCalculator.updateBalance` method is functioning correctly. Ensure its behavior remains unchanged after refactoring.
- The final solution must include **exactly two API endpoints**. Do not develop additional endpoints.
- **Do not** create a pull request or a new branch in the ikigai-digital repository. Instead, fork the repository into your own GitHub repository and develop the solution there.
- Handling invalid input or exceptions is not required.
- Use any tools, frameworks, or libraries you find suitable.
- In case of ambiguity, make logical assumptions and justify them in code comments.

### Preferred Stack
- Use an OpenAPI Swagger contract.
- Embrace Hexagonal Architecture.
- Follow atomic commit practices.
- Utilize testcontainers.
- Leverage AI-assisted development tools for code generation, testing, and refactoring.
