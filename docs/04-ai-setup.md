# AI Setup

This document answers requirement 6 of the assignment: the tools and setup used, the rules and prompts that steered the agents, and which parts of the solution were AI-assisted and why.

## 1. Tools

- **Claude Code** (Anthropic's CLI) runs the agents. JDK 21 and Docker are the only local requirements; Maven comes from the wrapper.
- **Models.** The coordinating session ran on Claude Fable 5.2 and handed work to subagents chosen by difficulty:
  - Claude Opus for architecture and design
  - Claude Sonnet for implementation and for the step reviews
  - Claude Haiku for mechanical steps (the build skeleton, the Liquibase changelog)
- **BMad Method** (`bmm` module) is installed locally as Claude Code skills and is not committed. It was used for orientation (`bmad-help`), for the project-context block in `CLAUDE.md` (`bmad-project-context`) and as the outline of the architecture document (`bmad-architecture`). The implementation steps were not run through BMad's story workflow; each was a brief written by the coordinating session and sent to a subagent.

## 3. Approach and workflow

One coordinating session plans the work, briefs subagents and checks their results; it works under the rules in [06-coordinator-playbook.md](06-coordinator-playbook.md). Each step went through the same loop: an executor subagent, an independent reviewer subagent, findings applied or rejected, the tests run and the diff read, then a local atomic commit.

| Step | What was done | Model | How it was verified |
|------|---------------|-------|---------------------|
| Characterization tests | `updateBalance` pinned on the untouched legacy code: plan rules, day boundaries, unknown plans, rounding | Sonnet | Green on the legacy code; deliberate breakages of the calculator (rounding mode, boundaries, rates, letter case) all caught |
| Architecture | The architecture document, then a revision after a review of its decisions | Opus | Reviewed by a separate agent, then read and corrected by hand |
| Skeleton and schema | Spring Boot and Maven wrapper setup, Testcontainers, the Liquibase schema | Haiku | Build green; the app started and the tables inspected in the running database |
| Domain refactoring | The plan logic replaced by one policy per plan behind the unchanged `updateBalance`; `ArchitectureTest` added | Sonnet | Characterization tests unchanged and green; old and new calculator compared on generated inputs |
| GET endpoint | Read side of the JDBC adapter, service, controller, mapper, DTOs and API test | Sonnet | API test against PostgreSQL with a full-body comparison and a dataset check; the test proved able to fail |
| POST endpoint | Write side of the adapter, the balance update, the endpoint and its API test | Sonnet | Expected dataset with hand-calculated balances; the test proved able to fail |
| OpenAPI contract | The generated contract pinned by a strict test against a committed file | Sonnet | The committed contract read by hand; an extra operation fails the test |
| Documentation | The README and this document | Sonnet | Every README command run; balances compared with a hand calculation; links checked |
| Code review and clean-up | The finished code read line by line; the remarks discussed one by one and applied: fewer comments, named constants, one JDBC API, OpenAPI metadata in one class, scenario tables in the unit test, Docker Compose for the local run | Opus to record the remarks, Fable to apply them | Full test run on every commit; the new ArchUnit rule and the empty withdrawals dataset proved able to fail; the app started locally and both endpoints called |
| Independent final review | The branch reviewed from the tracked files and the assignment text only, as an outside reviewer would see it; its findings applied: explicit null checks, three more unit cases, logging, cleaner documents | Fable | Old and new calculator compared on a boundary grid and on random inputs; every commit built and tested; the README instructions followed literally |

## 4. What was AI-assisted, and why

Code, tests and documents were generated by AI agents and reviewed step by step. Parts of the calculator, the policies and the tests were edited by hand during the code review.

**Decided by hand, not by the agents:**

- The approach: behaviour pinned by tests first, then the refactoring, in small steps.
- The test rules in [05-test-requirements.md](05-test-requirements.md).
- Plan codes as an enum with an `UNKNOWN` fallback, holding codes only; rates and day windows live in the policies.
- Plan codes stay case-sensitive, as in the legacy code; the questionable consequence is a known issue, not a fix.
- `updateBalance` stays short: a map from plan to policy, no `if` chains.
- The legacy classes stay in the root package, and the policies are listed in the calculator's no-arg constructor instead of being injected, for backward compatibility.
- The REST adapter has its own DTOs and a hand-written mapper; there are no persistence model classes; no interface has a single implementation and a single caller.
- Balances are stored without rounding, there is no guard against repeated updates and no locking. All three are written down as assumptions and known issues.
- The comment convention: a comment says why, never what.

**Why AI was used this way:**

- Speed on mechanical work: build setup, changelog, DTOs, mapping, repetitive boundary tests.
- Independent review: a separate agent reads each change with fresh context and without the executor's blind spots.
- Checks that are tedious by hand: breaking the code to see each new test go red, and comparing the old and the new calculator on generated inputs.

**Where human judgement was kept:** the interpretation of the requirements, the trade-offs between simplicity and extensibility, and the behaviour-preservation decisions.
